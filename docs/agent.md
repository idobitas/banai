# AI Agent (Phase 5)

The agent turns customer messages into **proposals**. It never changes the design: the customer confirms, and the server applies the signed proposal on the authoritative engine.

## Flow
1. `POST /api/chat {messages, design, revision}`. The chat sends the conversation (customer and assistant turns only) with the latest committed design and revision.
2. `backend/app/agent/service.py::run_turn` calls the model with the instructions (`prompt.py`) and one tool, `propose_changes` (`tools.py`).
   - A text answer (for example a clarification question) becomes the reply.
   - A tool call is validated with Pydantic, its ops are parsed with the domain op union, and they are **dry-run** with `apply_ops` on a copy of the design. A rejected call goes back to the model with the engine's error code and path, for up to 2 repairs. After that the customer gets a short clarification request.
3. The response is `{reply, proposal | null}`. The proposal is `{proposalId, baseRevision, baseHash, summary, changes, ops, signature}`. The signature is an HMAC-SHA256 over `(proposalId, ops, baseRevision, baseHash)` with `PROPOSAL_SIGNING_KEY` (`signing.py`). The server stores nothing.
4. Confirm sends `POST /api/proposals/apply {design, revision, proposal}`:
   - a bad signature returns **400 INVALID_PROPOSAL**;
   - a different revision or design hash returns **409 STALE**;
   - otherwise the server applies the ops and returns `{design, revision + 1}`. The client commits it with `store.replaceDesign`, which re-validates it.
5. Cancel only drops the proposal on the client. A manual edit bumps the revision, so the card turns stale.

Ids for new components are generated by the engine when the proposal is applied on the server. The client receives that resulting design, so a deterministic replay of the dry run is not needed.

## Persona (`prompt.py`)
- **Scope:** one standard straight wardrobe. Anything else gets one sentence steering back. It never claims a design is ready for manufacturing, and gives no prices or engineering advice.
- **Style:** 1 to 3 short sentences. Centimetres for the customer, integer millimetres in ops.
- **Language:** the server detects the language of the latest customer message (`reply_language`: Hebrew, English, or "same as the customer") and tells the model explicitly. Asking the model alone led to replies in Spanish and Dutch during evaluation.
- **Dad jokes:** paced by the server, not the model: one on every 4th customer message (`JOKE_EVERY`), never in a clarification question.
- **Safety:** the design JSON and customer text are data. The prompt tells the model to ignore instructions inside them (for example custom colour names). This is defence in depth only: the real protection is that ops are validated, nothing applies without Confirm, and all text is rendered with `textContent`.

## Configuration (`backend/.env`)
| Variable | Purpose |
|---|---|
| `OPENAI_API_KEY` | OpenAI key. Without it, `/api/chat` returns 503 and the chat says the assistant is unavailable. |
| `OPENAI_CHAT_MODEL` | Defaults to `gpt-5.4-mini` (configurable default, not a business rule). Blank values fall back to the default. |
| `PROPOSAL_SIGNING_KEY` | HMAC key for proposals. Use a long random value per environment. |

`APP_ENV=e2e` swaps OpenAI for `scripted.py`, a deterministic stand-in used by Playwright. It needs no key and has no cost.

## Limits
- 20 chat requests per minute per client IP (`ratelimit.py`, in memory, per process).
- The last 12 messages, each ≤ 2,000 characters. At most 3 model calls per request. 30 s timeout. `max_output_tokens` is 4,000.
- At most 100 ops per proposal, plus the engine's structural caps.

## Testing
- `backend/tests/test_agent.py`: fake LLM, no network. Covers signing, repair, fallback, stale, tampering, rate limit, language, joke pacing, and key hygiene.
- `frontend/tests/unit/chat/agentChat.test.js`: the chat model, the API client and `replaceDesign`.
- `frontend/tests/e2e/agent.spec.js`: the scripted agent end to end (Confirm, Cancel, stale, clarification, typing).
- `backend/scripts/agent_eval.py`: a **manual** live run against the real model (costs a few cents). It covers a full description, a vague request, an off-topic question, Hebrew, a single change, a manufacturing claim, and a joke turn.

## Known limitations (to address in Phase 9)
- Behind Railway's proxy, `request.client.host` is the proxy's address. Uvicorn must run with `--proxy-headers` (trusted forwarders) so the rate limit is per customer, not global.
- There is no request body size limit at the app level. Rely on the platform limit, or add one in Phase 9.
